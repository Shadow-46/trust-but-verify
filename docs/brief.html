Trust, but verify

Team: WASD — Shadow-46, Lomada-Sahithi · Repository: https://github.com/Shadow-46/trust-but-verify ([COMMIT]) · Demo: echo '{…}' | node track4_service.mjs · console: cd dashboard && npm run dev

Unique selling proposition

When a device is lost or a key must rotate, most systems keep trusting stale credentials and cannot prove what they decided. Our prototype revokes a device on every node in about 20 ms, rotates keys with a documented cutoff while transfers finish, protects files and messages with post-quantum cryptography against "harvest now, decrypt later", and — the core differentiator — every allow and every block carries a plain-language reason in an ML-DSA-signed, tamper-evident log. It fails closed on any integrity doubt, including an attacker rolling state back to undo a revocation. Zero dependencies: only vetted node:crypto (OpenSSL 3.5) primitives, no custom crypto, no ML.

Architecture

client/device ──signed request (ML-DSA-65)──▶ node ×3 ──verify sig · owner · device · revocation · nonce · key version──▶ allow/deny + reason control plane ──policy epoch n, ML-DSA-signed──▶ nodes (reject forged or older epochs; keep last verified policy offline) judge worker ──JSON──▶ track4_service.mjs ─▶ validate ─▶ policy ─▶ AES-256-GCM vault ─▶ signed hash-chained audit log peer A ◀──X25519 + ML-KEM-768 hybrid handshake, transcript signed──▶ peer B (AES-GCM chunks, recipient-bound) access logs ──▶ rule + approval + service-edge-graph detector ──▶ explained alerts (operator console)
  • Identity & authorization: each request is checked against the signed policy: asset exists, actor owns it, actor/device not disabled or revoked, request signature, ±30 s timestamp, single-use nonce, key version within its window. The decision and reason are written durably before replying.
  • Keys: master key (or KMS via TRACK4_MASTER_KEY) → HKDF → key-encryption key, state-MAC key; versioned data keys wrapped by the KEK. Rotation: grace period applies (30 s default) then every node rejects the old version; stored files re-encrypted in one atomic commit.
  • Recovery & integrity: atomic writes, PID-checked locks, state version bound to a signed log head (rollback and truncation detected), signed and digested backups whose restore keeps later revocations.
  • Messaging: forward-secret hybrid sessions, AAD binding of sender/recipient/message/position, duplicate refusal, reassembly under loss/reordering with reported failures, resumption bound to the peer's identity key.
  • Libraries: Node 24.11.1 built-ins only (ML-KEM-768, ML-DSA-65, X25519, AES-256-GCM, HKDF/HMAC-SHA-256); Next.js only for the demo console.

One-page threat model

Assets

AssetPropertyAssetProperty
File bodies, messagesConfidentiality (incl. future quantum), integrity, recipient bindingPolicy: owners, devices, revocations, key versionsIntegrity, freshness (no rollback)
Master, data, signing keysConfidentialityAudit / key-event logIntegrity, completeness, true actor

Adversaries

  • Unauthorized caller — malformed input, other users' IDs, injection, __proto__, path tricks.
  • Lost/stolen device holder — has the device key, keeps trying after revocation.
  • Compromised valid account — unexpected privilege gain, lateral movement with valid credentials.
  • Network attacker — records, replays, re-addresses, drops, reorders, swaps handshake keys; later may hold a quantum computer or stolen identity keys.
  • Local attacker without keys — edits, rolls back or truncates state, logs, backups, policy; plants symlinks in shared temp.

Trust boundaries & assumptions

Request → adapter (validation, identity, policy, audit) · control plane → nodes (signed epochs) · device → node (signed requests) · peer ↔ peer (signed hybrid handshake) · storage (MAC'd state, AES-GCM bodies, signed log/backups). We assume correct OpenSSL 3.5 primitives, out-of-band provisioning of the trust anchor and identity keys, key files private to the service user or a KMS-held master key, node clocks within ±30 s, and setup as a trusted operator action.

Limits and remaining risks (honest scope)

  • Largest risk: full host compromise (keys + disk) allows decryption and a consistent rollback of state and log together; mitigation is an external KMS and shipping signed log heads to a witness (not built).
  • No HSM; key erasure relies on Node process memory. Node clocks shared in the propagation measurement.
  • Cluster transport is a shared filesystem; messaging is a tested library without network transport.
  • Detector accuracy measured on public practice data and our synthetic generator (same documented environment) — not production traffic.
  • Denial of service and side channels are out of scope.
